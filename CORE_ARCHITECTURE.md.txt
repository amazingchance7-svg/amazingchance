# Amazing Chance — Core Architecture

## 1. Purpose

This document defines the core architectural rules, business invariants,
transaction boundaries, security requirements, and failure-handling rules
for the Amazing Chance platform.

The rules in this document apply to all current and future platform clients:

- Web application
- Mobile application
- Telegram bot
- Administrative panel
- Partner API
- Background workers
- Payment webhooks

No client may bypass the core business services or write directly to critical
database tables.

---

## 2. Core principles

The platform must follow these principles:

1. Financial and ticket operations are executed atomically.
2. Every external request that can be retried must be idempotent.
3. Database constraints are the final protection layer.
4. Business-critical state changes must be auditable.
5. Clients are never trusted.
6. Payment provider data is independently verified.
7. Draw results must be reproducible and publicly verifiable.
8. A failed operation must not leave partial business state.
9. Critical operations must be safe under concurrency.
10. Sensitive operations must follow least-privilege access.

---

## 3. Trust boundaries

The following inputs are untrusted:

- Browser requests
- Mobile application requests
- Telegram bot requests
- Partner API requests
- Payment webhook payloads
- HTTP headers
- Client-generated identifiers
- Client-provided prices
- Client-provided ticket counts
- Client-provided draw identifiers
- Administrative requests

All untrusted input must pass:

1. Authentication when required
2. Authorization
3. Schema validation
4. Business validation
5. Database constraints

The frontend must never be treated as a security boundary.

## 4. System ownership rules

### 4.1 PurchasesService

PurchasesService owns the purchase lifecycle.

It is responsible for:

- Creating purchases
- Calculating authoritative purchase amounts
- Validating purchase transitions
- Confirming successful payments
- Orchestrating ticket allocation
- Updating purchase status
- Writing purchase state events

No other service may directly change Purchase.status.

### 4.2 TicketAllocationService

TicketAllocationService owns ticket-number range reservation.

It is responsible only for:

- Finding an existing allocation for a purchase
- Initializing a draw ticket sequence
- Atomically reserving a number range
- Creating TicketAllocation

It does not:

- Load payment information
- Verify purchase status
- Create Ticket records
- Update Purchase status
- Send notifications

### 4.3 TicketsService

TicketsService owns Ticket record creation.

It is responsible only for:

- Validating an allocated range
- Creating Ticket records
- Verifying the expected number of records was created

It does not:

- Reserve ticket numbers
- Verify payments
- Update purchases
- Complete draws

### 4.4 PaymentsService

PaymentsService owns payment records and provider interaction.

It is responsible for:

- Creating payment attempts
- Storing provider references
- Verifying provider responses
- Processing verified webhook events
- Enforcing webhook idempotency
- Recording payment state transitions

PaymentsService must never trust an amount sent by the client.

### 4.5 LotteryDrawsService

LotteryDrawsService owns draw lifecycle rules.

It is responsible for:

- Creating draws
- Opening ticket sales
- Closing ticket sales
- Preventing purchases after closure
- Starting draw execution
- Finalizing draw results
- Publishing verification data

## 5. Core business invariants

The following invariants must always remain true.

### 5.1 Purchase invariants

- Every purchase belongs to exactly one user.
- Every purchase belongs to exactly one draw.
- A purchase price is calculated by the backend.
- A purchase currency cannot change after payment initialization.
- A completed purchase must have a successful confirmed payment.
- A completed purchase must have exactly one TicketAllocation.
- A completed purchase must have the expected number of Ticket records.
- A purchase cannot transition backward unless an explicit compensating
  workflow exists.
- The same idempotency key cannot create multiple purchases.

### 5.2 Ticket invariants

- Every Ticket belongs to exactly one purchase.
- Every Ticket belongs to exactly one draw.
- A ticket number is unique within a draw.
- A ticket cannot exist without an allocation.
- Ticket numbers in one allocation must form one continuous range.
- Allocation range size must equal the purchase ticket count.
- The same purchase cannot have multiple allocations.
- Ticket numbers are never assigned manually.
- Tickets are created only after successful payment confirmation.

### 5.3 Draw invariants

- Ticket sales are allowed only while the draw is OPEN.
- A CLOSED draw cannot accept new purchases.
- A draw cannot be executed before ticket sales close.
- A finalized draw result is immutable.
- Winning-ticket calculation must use published verification inputs.
- Draw execution must be idempotent.
- A draw can have only one final result.

### 5.4 Payment invariants

- A provider event can be processed only once.
- Payment amount must match the authoritative purchase amount.
- Payment currency must match the purchase currency.
- Payment provider reference must be unique where the provider guarantees
  uniqueness.
- A payment marked successful must contain provider-verification evidence.
- An invalid webhook signature must never cause a state change.
- A client redirect is not proof of successful payment.

## 6. Purchase status model

The purchase lifecycle must use explicit states.

Recommended states:

```text
PENDING_PAYMENT
PAYMENT_PROCESSING
PAYMENT_CONFIRMED
TICKET_ALLOCATION_PENDING
COMPLETED
PAYMENT_FAILED
EXPIRED
CANCELLED
REFUND_PENDING
REFUNDED
6.1 Allowed transitions
PENDING_PAYMENT
  -> PAYMENT_PROCESSING
  -> PAYMENT_FAILED
  -> EXPIRED
  -> CANCELLED

PAYMENT_PROCESSING
  -> PAYMENT_CONFIRMED
  -> PAYMENT_FAILED
  -> EXPIRED

PAYMENT_CONFIRMED
  -> TICKET_ALLOCATION_PENDING

TICKET_ALLOCATION_PENDING
  -> COMPLETED

COMPLETED
  -> REFUND_PENDING

REFUND_PENDING
  -> REFUNDED

Any transition not explicitly defined is forbidden.

Status transitions must be implemented as conditional database updates or
performed while the purchase row is locked.

7. Payment confirmation flow

A successful payment flow is:

Payment provider
    |
    v
Webhook endpoint
    |
    v
Verify provider signature
    |
    v
Validate webhook schema
    |
    v
Find provider event by unique event ID
    |
    v
Return success if already processed
    |
    v
Load payment and purchase
    |
    v
Verify provider account
    |
    v
Verify amount
    |
    v
Verify currency
    |
    v
Verify payment reference
    |
    v
Begin serializable transaction
    |
    +-- Lock or conditionally update purchase
    +-- Confirm payment state
    +-- Record provider event
    +-- Reserve ticket-number range
    +-- Create TicketAllocation
    +-- Create Ticket records
    +-- Update purchase to COMPLETED
    +-- Write PurchaseStateEvent records
    +-- Write audit record
    |
    v
Commit
    |
    v
Return provider acknowledgement

The webhook acknowledgement must not be sent before the transaction commits.

8. Ticket allocation transaction

Ticket allocation, ticket creation, purchase completion, and audit recording
must participate in the same database transaction.

Required order:

1. Load or lock purchase
2. Verify purchase status
3. Verify draw is eligible
4. Check existing allocation
5. Reserve number range atomically
6. Create TicketAllocation
7. Create Ticket records
8. Verify created ticket count
9. Update purchase status
10. Create PurchaseStateEvent
11. Create audit record
12. Commit transaction

If any step fails, the entire transaction must roll back.

A reserved ticket range must not survive without its Ticket records and
completed purchase state.

9. Ticket sequence rules

Each draw has exactly one TicketSequence row.

TicketSequence.nextNumber contains the next unallocated ticket number.

Initial state:

nextNumber = 1

For a purchase of 5 tickets:

reserved range = 1..5
new nextNumber = 6

The range must be reserved with one atomic PostgreSQL statement:

UPDATE "ticket_sequences"
SET
  "nextNumber" = "nextNumber" + $ticketCount,
  "updatedAt" = NOW()
WHERE "drawId" = $drawId
RETURNING
  "nextNumber" - $ticketCount AS "startNumber",
  "nextNumber" - 1 AS "endNumber";

The application must never:

Read nextNumber
Calculate values in application memory
Write nextNumber afterward

That pattern is vulnerable to race conditions.

10. Transaction isolation and retries

Critical financial and ticket-allocation transactions must use PostgreSQL
SERIALIZABLE isolation.

Serializable transactions can legitimately fail because of concurrent
activity.

The application must retry only recognized transient database errors.

Recommended retry policy:

Maximum attempts: 3
Delay: randomized exponential backoff
Attempt 1 delay: 25–75 ms
Attempt 2 delay: 75–200 ms
Attempt 3 delay: 200–500 ms

Do not retry:

Validation errors
Authorization errors
Invalid status transitions
Amount mismatches
Invalid signatures
Permanent unique-constraint violations
Unknown programming errors

A retry must execute the entire transaction again.

11. Idempotency

Idempotency is required for:

Purchase creation
Payment initialization
Payment webhooks
Ticket allocation
Draw execution
Refund requests
Administrative critical actions
11.1 Idempotency key rules

An idempotency key must:

Be generated by a trusted client or backend
Be unique within an operation scope
Be stored in the database
Be linked to the authenticated actor where applicable
Return the original operation result on retry
Reject reuse with a different payload

The platform should store a normalized request hash with the idempotency key.

If the same key is reused with a different request hash, the operation must
fail with a conflict error.

11.2 Ticket-allocation idempotency

TicketAllocation.purchaseId must be unique.

A repeated allocation request must return the existing allocation.

It must not reserve a second range.

12. Required database constraints

Application validation is not sufficient.

The database must enforce critical invariants.

Required constraints include:

UNIQUE Purchase.idempotencyKey
UNIQUE TicketAllocation.purchaseId
UNIQUE Ticket(drawId, numberInDraw)
UNIQUE provider webhook event identifier
UNIQUE final draw result per draw

Required checks include:

Purchase.ticketCount > 0
TicketAllocation.startNumber > 0
TicketAllocation.endNumber >= TicketAllocation.startNumber
TicketSequence.nextNumber > 0
Monetary amounts >= 0

Foreign keys must be explicit.

Critical records should normally use ON DELETE RESTRICT.

Cascade deletion must not be used for financial, ticket, payment, audit, or
draw-result history unless there is a documented legal requirement.

13. Monetary values

Floating-point types must never be used for money.

Allowed approaches:

Integer minor units
PostgreSQL NUMERIC with explicit precision and scale

Preferred internal representation:

1 USD = 100 minor units

Example:

ticket price = 100
currency = USD

The backend must calculate:

totalAmount = authoritativeTicketPrice * ticketCount

The client-provided total amount must be ignored.

Every monetary value must include an explicit currency.

14. Authentication and authorization

Authentication proves identity.

Authorization determines allowed actions.

The platform must use:

Short-lived access tokens
Rotating refresh tokens
Refresh-token reuse detection
Password hashing with a memory-hard algorithm
Rate limiting
Session revocation
Audit logging for security events

Administrative access must use:

Separate roles and permissions
Mandatory multi-factor authentication
Stronger session policies
IP and device monitoring where appropriate
Step-up authentication for critical actions

Roles alone are insufficient for sensitive operations.

Permission checks must be explicit.

15. Webhook security

Every payment webhook must:

Use HTTPS
Verify provider signature
Verify timestamp where supported
Reject stale events where supported
Store provider event ID
Enforce event ID uniqueness
Validate provider account or merchant ID
Verify payment reference
Verify amount
Verify currency
Process events idempotently
Log verification failures without exposing secrets

Webhook raw body must be retained temporarily when the provider signature
depends on exact request bytes.

Webhook endpoints must not depend on browser authentication.

16. API security

The API must implement:

Strict DTO validation
Rejection of unknown properties where appropriate
Request-size limits
Rate limiting
Authentication throttling
CORS allowlists
Secure HTTP headers
Explicit content types
Sanitized error responses
Correlation IDs
Structured logging

Production responses must not expose:

Stack traces
SQL queries
Internal filesystem paths
Secret values
Provider credentials
Internal database identifiers when public identifiers are available
17. Public and internal identifiers

Internal database identifiers may use UUIDs.

Public resources should use dedicated non-sequential public IDs.

Examples:

PUR_...
DRW_...
TKT_...
PAY_...

Public IDs must not expose:

Record counts
Database ordering
Internal topology
Sensitive business volume

Public IDs are not authorization controls.

Every resource lookup must still verify ownership or permission.

19. Logging rules

Logs must be structured.

Every critical request must include:

requestId
correlationId
actorId where known
public resource ID where applicable
operation name
result
duration
error code

Logs must never contain:

Passwords
Access tokens
Refresh tokens
Payment credentials
Full card data
Webhook secrets
Private cryptographic keys

Expected business errors should not be logged as system crashes.

20. Error handling

Errors must be classified.

Recommended categories:

VALIDATION_ERROR
AUTHENTICATION_REQUIRED
FORBIDDEN
RESOURCE_NOT_FOUND
CONFLICT
INVALID_STATE_TRANSITION
PAYMENT_VERIFICATION_FAILED
IDEMPOTENCY_CONFLICT
RATE_LIMITED
DATABASE_TRANSIENT_ERROR
INTERNAL_ERROR

The API must return stable machine-readable error codes.

Internal exceptions must be converted to sanitized public responses.

Unknown errors must not be silently swallowed.

21. Draw integrity

Draw execution must be isolated from normal request processing.

A draw must not use an uncommitted or mutable ticket set.

Before execution:

Draw status must be CLOSED.
Ticket sales must be disabled.
The final eligible ticket count must be recorded.
A deterministic ticket-set digest must be calculated.
Required public randomness commitments must be stored.
Execution must acquire a draw-level lock.

After execution:

Winning result must be stored atomically.
Verification inputs must be stored.
Verification output must be reproducible.
Draw status must become FINALIZED.
Result must become immutable.
Publication must not alter the stored result.

No administrator may manually choose a winning ticket.

22. Randomness and provable fairness

The final randomness design must use a commit-reveal or equivalent
publicly verifiable mechanism.

The platform must publish enough information to allow independent
verification of:

The eligible ticket set
The ticket-set ordering
The randomness inputs
The randomness derivation
The winner-selection algorithm
The resulting winning ticket or tickets

Secret values must be committed before they are revealed.

A secret commitment must use a cryptographically secure hash.

The exact algorithm and canonical serialization format must be versioned.

23. Background processing

Non-critical side effects should run after the core transaction commits.

Examples:

Email notifications
Telegram notifications
Analytics events
Marketing events
Non-critical reporting

These actions must use an outbox pattern.

The database transaction should:

Complete the business operation
Write an OutboxEvent
Commit

A worker then publishes or processes the event.

This prevents committed purchases from losing notifications because of
process crashes.

Notifications must never determine whether a purchase transaction succeeds.

24. Administrative safety

Critical administrative actions require:

Explicit permission
Multi-factor authentication
Re-authentication where appropriate
Reason field
Audit event
Idempotency
Confirmation step for destructive actions

Recommended two-person approval for:

Manual refunds above a threshold
Draw cancellation
Draw-result emergency procedures
Changes to fairness configuration
Changes to payment routing
Changes to privileged roles

Direct database modification is forbidden during normal operations.

Emergency database intervention must be documented and audited separately.

25. Data deletion and retention

Financial, ticket, draw, and audit history must not be physically deleted
through normal application APIs.

User privacy deletion should use:

Anonymization
Pseudonymization
Removal of non-required personal fields
Retention of legally required transaction records

Retention periods must later be aligned with the legal jurisdictions in which
the platform operates.

29. Current ticket-allocation contract

The current internal service contract is:

reserveRange(
  tx: Prisma.TransactionClient,
  input: {
    purchaseId: string;
    drawId: string;
    ticketCount: number;
    correlationId: string;
  },
): Promise<{
  allocation: TicketAllocation;
  alreadyAllocated: boolean;
}>;

Rules:

The caller owns the transaction.
The caller validates the purchase and draw.
The service reserves the range atomically.
The service creates TicketAllocation.
The caller creates Ticket records.
The caller completes the purchase.
All operations occur before the same transaction commits.
30. Definition of transaction success

A paid ticket purchase is successful only when all of the following are
committed:

Payment is confirmed
Purchase has final valid status
TicketAllocation exists
Expected Ticket records exist
PurchaseStateEvent exists
Audit record exists

Anything less is a failed transaction and must roll back.

A payment-provider retry must then be able to safely repeat the operation.
